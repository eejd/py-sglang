## Question

QB #406's >=33.412 GiB kernel-peak sum was the **second of two sequential requests** (chunk 4096, pool 36864, output target 128, seed 505645418): request 1 completed (32802 input / cached 1 / output 128), request 2 errored (client prompt count 32768, output 64, cached null) and no footprint sample lies between request 1's end and request 2's growth. ES's accepted 32k single-request run reproduced the lazy-scatter (WP1 H4 / diagnosis H1) retained-active quantity (12928.12 MiB gap vs 12928 predicted) but not 33 GiB. This record (1) reconstructs the two-request timeline offline with every quantity labelled by domain, and (2) runs controlled engine contrasts that separate request history, prefix replay, allocator clearing, chunk geometry, pool size and decode depth. Deliverable: request/phase-resolved accounting plus bounded causal contrasts with explicit unknowns and lower bounds; not an unqualified root cause, and not a promise to complete the historical high-memory request.

**Growth-formula finding made offline, before any live data.** On every legacy observe/eval-pool pair (10 pairs) the cumulative growth `D_j - D_0` follows `sum(cap_k x 32 KiB, k = 0..j-1)` within 160 MiB at every `j` (largest lag-form residual 9.95 MiB), while the planned form `sum(k = 1..j)` fails at multi-doubling geometry (largest residuals about 906 MiB at 16384 and about 1924 MiB at 32768). A one-chunk lag (`chunk.after` precedes realization of the current chunk's version) is a **hypothesis** for the offset, not a measurement. The **planned form is the primary preregistered verdict** (tolerance 160 MiB absolute on the cumulative residual at each `j >= 1`), reported unchanged, and a failure is recorded as such; the lag form is an additional secondary prediction (legacy data motivated it, so it is a confirmation attempt on new geometry: chunk 4096, no warmup, two-request histories; not an independent discovery). Neither verdict is retuned after live data.

## Smoke gate (stage 1)

Mechanically checked by `causal_report.py live` (hard failures): both request identities and body hashes match the fixture hashes (output-128 cells; output-32 bodies differ only in `max_completion_tokens`, which `sequence.py` overrides after the spec-time fixture hash validation, so their body hash is not independently derivable offline); sends do not overlap and the q1-terminal-to-q2-send gap is nonnegative (no timing threshold); complete SSE with usage; exact shim `req_id` == RID (or response ID) for q1 and q2; attributable decode, release and interventions (also enforced by the runner's `intervention_evidence`); observed input = measured prefix + sum(new tokens); `runner_init.pool_size` equals the variant pool and every executed chunk is at most the variant chunk size; engine completed and cleanup confirmed; expected cell set present. Checked mechanically by `run_stage.sh`: free disk >= 20 GiB, normal memory pressure with >= 13 % free, no `Swapouts` growth between pre and post host records, port free, identities intact. Checked by hand against the harvested `outcome.json`: that the host/safety monitor saw no pressure change during the run. Observe may execute fewer than two chunks on a full-prefix-hit identical q2 (zero chunks require client cached tokens equal to observed input and explicit completion/decode evidence); fidelity is judged on chunks actually executed. Cell statuses `complete`, `lower_bound`, `incomplete`, `not_run`; stage 4 additionally reports `incomplete_single_repeat_lower_bound` when repeat 1 is a confirmed-cap lower bound and repeat 2 is `not_run`.

## Hard failures vs scientific findings (defined identically in verifier, report, this file)

**Hard (stop the matrix; all later cells/stages `not_run`):** a cap, death, safety/pressure trip, swap growth, timeout, failed/unreadable engine, ownership/identity uncertainty, unconfirmed cleanup, wrong/missing RID, unmatched/duplicated intervention application, unknown peer or health traffic inside the sequence, missing required completion/release, token-equation failure, failed fidelity/attribution in stages 1-3. In stage 4 the same events are preserved as the outcome (a cap is a lower bound, repeat 2 then `not_run`, stage status `incomplete_single_repeat_lower_bound`); nothing is retried and no cap or deadline is raised. **Scientific (reported, later independent tests continue):** matched-ID geometry/work differs (`non_isolated`), a distinct q2 with fewer than two chunks, no sampled q1 settled interval, a failed numerical contrast. An unexplained successful or failed contrast is a finding, not a safety failure.

## Interpretation rules (fixed before any live run)

Pair cells only within the same repeat, size, pool, chunk, output depth, request count and relation: 16k distinct observe c4096 <-> distinct eval-pool c4096, identical observe <-> identical eval-pool; 32k identical observe <-> identical eval-pool (bridge), stage-4 distinct observe <-> that repeat's distinct eval-pool bridge cell. No pairing of observe c2048 with eval-pool c4096, nor across repeats/relations. Require equal canonical input hashes, observed input/output and per-chunk `new_tokens/prefix_len/capacity` sequences; otherwise `non_isolated`.

* **Lazy-scatter growth (prospective, within request).** Observe post-chunk active = `chunk.after.mx.active`; eval-pool post-chunk active = the matching selected `intervention_applied.after.mx.active`; `D_j` = observe - eval-pool, `D_0` = chunk 0 of the SAME request (q2 uses q2's own chunk 0). Planned form: `|(D_j - D_0) - sum_{k=1..j} cap_k x 32 KiB| <= 160 MiB` for every `j >= 1`; lag form (offline finding): `sum_{k=0..j-1}`. One correctly ordered application per matched chunk; missing/duplicate/ambiguous applications make the chunk and the rest of that request `incomplete`, never a contradiction. A complete positive result needs both planned repeats. Identical full-prefix-hit q2 with 0/1 chunk has no growth test. A failed completed test contradicts that numerical form; it is never retuned.
* **Carryover (descriptive, no tolerance verdict):** `D_0(q2) - D_0(q1)`, final q2 active gap, q1/q2 capacity sums and their sum. A q1 settled value exists only if a sample lies between q1 release and q2 send. A capped request yields its observed trajectory/prefix as a **lower bound** only.
* **Allocator retention:** clear-cache cells: report cache freed, active and footprint change at each boundary; selective effect = cache decrease >= 64 MiB and |active change| <= 16 MiB. Decode/release growth is not isolated by a per-prefill intervention; a small effect does not refute caching everywhere.
* **Parked/private caches and pool realization:** require q1 removal/acquisition metadata and q2's measured initial capacity before claiming reuse; metadata bytes are never added to active/footprint; the small 128 MiB term is claimed as a retained small cache only if the trace shows it.
* **Pool and output depth:** bridge cells 1 vs 3 isolate pool (2048 tokens = 64 MiB nominal payload plus padding); 2 vs 3 isolate output depth (decode/history effects, not specifically logits).
* **Logits / in-flight pinning / non-MLX overhead:** source/window bounds only; without branch/allocation instrumentation or an independent synchronization intervention these stay `not_identifiable` or `consistent_but_not_isolated`. No invasive engine change is made.
* **#406 reconciliation** only with comparable domains, baselines, ordinals and work; similar peaks alone establish nothing. The 27904 MiB scheduler cap is `configured_not_read_back`, scheduler-role proof only, no proven aggregate enforcement.
