## Comparison

| Engine | KV allocation and behavior at limits | Predictability |
|---|---|---|
| **mlx_lm** | Contiguous KV grows on demand in 256-token increments. Optional rotating cache overwrites old context; the server evicts retained prompt caches, not necessarily active KV. [Local cache.py:339–369,423–525](file:///opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/mlx_lm/models/cache.py#L339) | KV payload is estimable from context and dtype; active allocations, transients and total process footprint are not bounded by the server’s retained-cache cap. |
| **llama.cpp** | A context-sized KV buffer is preallocated; slots share it when unified KV is enabled. Context shifting is optional; prompt-cache reuse and idle-slot eviction are configurable. [KV design discussion](https://github.com/ggml-org/llama.cpp/discussions/21961), [server options](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) | Configured KV capacity is comparatively predictable, but model, compute buffers and OS residency remain additional. |
| **vLLM** | Startup allocates a budgeted KV pool; requests receive blocks as needed. Under contention, V1 can preempt and recompute requests. [Optimization guide](https://docs.vllm.ai/en/stable/configuration/optimization/), [block manager](https://docs.vllm.ai/en/stable/api/vllm/v1/core/kv_cache_utils/) | Fixed pool is predictable; it is not a guarantee of total process memory or freedom from allocation failure. |
| **vllm-metal** | Apple Silicon plugin uses vLLM scheduling and paged KV with MLX/Metal. Its documented memory guard profiles startup, budgets a fixed KV pool, caps MLX’s reusable buffer cache, and waits for pages when needed. [Project announcement](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0) | Closest documented Apple-specific budgeted-pool design; the documentation is not independent proof of a hard whole-process cap. |
| **Ollama** | `num_ctx` and parallelism determine context allocation; requests queue if models cannot fit, idle models unload, and an overflowing queue returns 503. [FAQ](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests) | Context allocation scales with context length × parallelism; other memory is extra. |
| **LM Studio** | Documents context length, Flash Attention, KV offload and batch controls for its llama.cpp engine, plus MLX KV quantization. [Load API](https://lmstudio.ai/docs/developer/rest/load), [release notes](https://lmstudio.ai/docs/api/ttl) | Exact active-cache allocation and limit behavior were **not found** in the load/API documentation searched. |

## Important qualifications

**mlx_lm.** `max_kv_size` selects `RotatingKVCache` only when the model does not provide its own `make_cache`; multi-token updates may temporarily reach `max_size + S - 1`, so it is not an exact instantaneous byte ceiling. `kv_bits` supports quantized caches. Prompt caches can be saved, loaded and trimmed; trimming ordinary `KVCache` reduces its offset rather than reallocating its backing arrays. [cache.py:16–40,43–138,251–300,391–394,462–480](file:///opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/mlx_lm/models/cache.py#L16).

The server defaults to ten retained prompt caches and optionally accepts a byte limit; it trims retained entries against the budget remaining after active cache bytes. That does **not** establish a hard limit on active KV or process memory. [server.py:1131–1134,2320–2329](file:///opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/mlx_lm/server.py#L1131). Generation explicitly evaluates cache state at prefill boundaries and calls `mx.clear_cache()`; the latter clears reusable allocator cache, not live arrays. [generate.py:437–480](file:///opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/mlx_lm/generate.py#L437). Its wired-limit helper uses the device recommendation and restores the previous limit after synchronization; this is not a process-memory cap. [utils.py:74–83](file:///opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/mlx_lm/utils.py#L74), [generate.py:237–272](file:///opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/mlx_lm/generate.py#L237).

**llama.cpp.** `--ctx-size`, `--parallel`, `--kv-unified`, `--cache-reuse`, `-ctk/-ctv`, and logical/physical batch sizes expose the principal tradeoffs. `--fit` adjusts **unset** parameters against device memory and a margin; it is not a hard process cap. On Metal, the backend reports free memory as recommended working set minus current Metal allocation, floored at zero, and notes that allocation can exceed the recommendation. [Server options](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Metal source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m). A universal queue/reject rule for all KV-exhaustion cases was **not found** in the server options inspected.

**vLLM.** Its startup cache planning checks available KV capacity against model-length requirements; `max_model_len=-1` can estimate a fitting length. Explicitly oversized cache allocation can fail at startup. [KV planning API](https://docs.vllm.ai/en/stable/api/vllm/v1/core/kv_cache_planning/), [optimization guide](https://docs.vllm.ai/en/stable/configuration/optimization/). The standard vLLM preemption behavior should not automatically be assumed for every vllm-metal model/version.

**Ollama.** Flash Attention and `OLLAMA_KV_CACHE_TYPE` provide a memory/quality tradeoff; its documentation quotes approximately half and quarter of f16 KV memory for q8 and q4 respectively. [FAQ](https://docs.ollama.com/faq#how-can-i-set-the-quantization-type-for-the-kv-cache).

## Retained versions and recommendation

mlx_lm itself uses lazy MLX concatenations and indexed updates, but it also evaluates prompt-cache state at each prefill boundary. **No evidence found** in the inspected mlx_lm code or cited llama.cpp, vLLM, Ollama and LM Studio documentation that they exhibit the *same measured per-chunk full-cache-version retention* as the reported SGLang MLX replay. That is not proof it cannot occur in another path.

**[INFERENCE]** For one to a few chats using remaining unified memory for a large model and KV, vllm-metal is the closest documented target for SGLang MLX: an explicit memory budget, fixed paged pool, bounded allocator cache, admission/waiting, and reported effective capacity. llama.cpp’s explicit context-sized allocation is a simpler alternative when predictable reservation matters more than sharing unused capacity. Neither design makes a token limit alone a whole-process memory guarantee.
