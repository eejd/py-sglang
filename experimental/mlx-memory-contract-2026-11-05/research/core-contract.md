## Core memory contract

**The documented contract is a bounded logical KV-token pool, not a hard bound on total device or process memory.** The tuning guide describes total memory as weights + KV pool + CUDA graph buffers + activations, with `mem_fraction_static` sizing the first two and headroom needed for the others. It explicitly warns that insufficient headroom can still cause OOM and recommends tuning chunk size and concurrency (`docs/docs/advanced_features/hyperparameter_tuning.mdx:33-65`). `--max-total-tokens` is documented as the maximum **tokens in the memory pool**, not a byte or process-memory limit (`docs/docs/advanced_features/server_arguments.mdx:440-465`).

| Evidence | Consequence |
|---|---|
| Core profiles currently free memory minus `pre_model_load_memory × (1 - mem_fraction_static)`, with additional special reservations; a standard configurator divides available bytes by per-token cost and page-aligns (`python/sglang/srt/mem_cache/kv_cache_configurator.py:2784-2832,2968-3020`; `python/sglang/srt/model_executor/pool_configurator.py:612-628`). | Static fraction is a **sizing policy**, not a runtime memory enforcer. Explicit token caps constrain the calculated pool. |
| `PrefillBudget` calls itself a “fixed token pool”; it counts allocator-available plus evictable tokens, pending allocations, and decode headroom (`python/sglang/srt/mem_cache/prefill_budget.py:62-63,91-105,114-140,156-168`). `PrefillAdder` obtains the budget from the allocator (`python/sglang/srt/managers/schedule_policy.py:625-649`). | Admission is in allocator-defined logical resources. **[Inference]** A backend with material memory outside that accounting must separately budget it if pool-based admission is to predict memory pressure. |
| Decode checks allocator capacity, evicts/retracts as needed and may abort the last request if even it cannot fit (`python/sglang/srt/managers/schedule_batch.py:3372-3418,3420-3498`). | Retraction addresses the allocator’s capacity gate, not arbitrary MLX allocations or total process footprint. |

I did **not find an explicit backend API statement requiring all backend allocations to fit within the token pool** in the searched tuning/server-argument documentation, `PrefillBudget`, scheduler admission/retraction, pool configurator and MLX comments. The stronger conclusion is an architectural inference from the accounting above, not a written universal requirement. Neither the pool nor static fraction is documented as bounding total device memory; activations and graph buffers are explicitly outside the static allocation.

## MLX design and stated rationale

- The upstream radix PR says its goals were feature parity and better shared-prefix prefill throughput. It introduced a shared MLX KV data store under the scheduler’s existing radix/slot allocator, plus separate prefill and contiguous decode caches ([SGLang PR #21509](https://github.com/sgl-project/sglang/pull/21509)).
- Installed MLX code says lazy pool scatters chain prior versions and retain their source cache slices. It evaluates them for auxiliary-state models because fresh per-request caches were retained and caused OOM; it skips evaluation for dense models because cache reuse appeared flat over 500 distinct requests and evaluation cost prefill latency (`/opt/local/Library/Frameworks/Python.framework/Versions/3.14/lib/python3.14/site-packages/sglang/srt/hardware_backend/mlx/model_runner.py:1046-1056`). Local commit `bd3ba7f41f` describes that selective decision. The supplied long-context replay is evidence outside that stated short-request observation.
- Dense cache acquisition resets and reuses a cache; `reset()` preserves its allocated buffers. The cache starts at 4096 tokens, grows by doubling and uses slice assignment rather than concatenation (`…/mlx/model_runner.py:318-336`; `…/mlx/kv_cache/attention_kv_cache.py:62-70,112-125,163-165`). I found **no explicit separate rationale** for the exact doubling factor or retained-capacity policy in the inspected comments, original radix PR description and file history; amortization/allocation avoidance is plausible but **[Inference]**, not a stated goal.
- A radix hit gathers its prefix into each request’s private contiguous cache, so shared pool occupancy counts a prefix once while private capacity can multiply across requests (`…/mlx/model_runner.py:755-760`; `…/mlx/kv_cache/private_cache_admission.py:1-15`). The installed hybrid-radix sizing reserves space for private caches, including growth, and its private-prefill budget accounts for concurrent private capacity; it expressly allows a lone request (`…/mlx/model_runner.py:723-745,763-770,794-830`; `…/mlx/kv_cache/private_cache_admission.py:47-65`). **This is not a general dense-model process-memory bound**: non-hybrid explicit pool sizes return directly and dense auto-sizing uses the ordinary KV budget (`…/mlx/model_runner.py:767-771,869-874`).

**Assessment:** The reported dense MLX growth is compatible with the narrow documented meaning of `--max-total-tokens`, but conflicts with the simpler weights-plus-one-KV-pool memory model users are encouraged to use for sizing. Neither that documentation nor scheduler retraction guarantees protection from private-cache and lazy-version memory outside allocator accounting.
